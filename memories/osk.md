Built 2026-11-08 to replace wvkbd, on niri 26.04+git20261107.9955d92 (user's own deb from `~/raoh/my-niri`, includes niri PR #4548 + smithay dmabuf v5 patch). Background and the pre-#4548 failure are in the niri project's `memories/osk.md`.

wvkbd on this niri: Ctrl state desyncs (UI shows Ctrl off but Space still switches fcitx5 IM, or the toggle does nothing). Cause (read in smithay 65aa86f `src/wayland/virtual_keyboard/mod.rs`): the `modifiers` request sets *absolute* masks shared with the seat's real keyboard state, which wvkbd uses for its sticky Ctrl. So `rtfs-vkbd` never sends `modifiers`; modifiers are real key press/release (Ctrl=29) and niri computes state like hardware. Keymap is `no_keymap` (format 0, fd /dev/null, size 0) = seat keymap, keycodes are evdev codes. Smithay releases held keys when the virtual keyboard is destroyed (helper exit).

Verified: Super+O via rtfs-vkbd toggles niri overview (binds see it); layout renders on eDP-1. User confirmed 2026-11-08: typing, bar toggle, all three modifier modes, Ctrl+Space and the main key combos with fcitx5, top mode over kitty (acceptable). User confirmed 2026-11-10: typing in the launcher search with the launcher's own OSK in tablet mode.

Windows shrink via the OSK's exclusive zone, including Mod+M `maximize-window-to-edges` (measured: Firefox 920 → 628 high; edge-to-edge has no border, so it can look like it didn't). kitty quick-access-terminal cannot: it is top-anchored with fixed `lines 840px`, layer-shell never resizes that, and its conf has no exclusive-zone option. Rejected fixes: smaller `lines` (user needs the space), runtime `kitten @ resize-os-window --action=os-panel` (needs remote control on that kitty = any user process can type into it). Chosen 2026-11-08: OSK translucency toggle (`Osk.translucent`; user tried 0.5, 0.65, then 0.8), exclusive zone unchanged; plus a top/bottom flip (`Osk.atTop`). Top mode first reserved a zone and pushed kitty's panel down off-screen (layer-shell moves, never resizes it), so top = `ExclusionMode.Normal` + `exclusiveZone: 0` (below the bar, pushes nothing; measured Firefox stays 920) and switching to top turns translucency on (user's choice). All three are settings since 2026-11-08: `osk.opacity` (%, default 80), `osk.topReserve` (default off), `osk.topTranslucent` (default on). Both keys sit right of the right Shift (user rarely uses it; Del stays 2 wide because it is used often).

Modifiers: tap = latched, double tap (400 ms) = locked with an official-gradient LED, hold while typing = real hold (user asked for both; tried hold-to-type with a finger on first use).

`qs ipc call <target> show` does not call a function named `show` (prints the target listing instead), so IPC uses open/close.

Modals (2026-11-08): the modal mask hides the bar button and, being an Overlay surface mapped later, also the OSK window (niri stacks same-layer surfaces by map order; an OSK opened *after* the modal was on top, opened before was dimmed under it). Chosen fix: the keyboard grid is `OskKeyboard.qml`; `DialogFrame` draws its own copy above the mask and `OskWindow` hides while `Osk.modals > 0` — deterministic, not relying on map order. The modal copy is `viewControls: false`: fixed at the bottom, always opaque, no translucency/flip keys (right Shift widened) — the user's call after the conditional-anchor flip bug; the card moves above the keyboard, so neither key is useful there. The modal button (`DialogOskButton`, bottom-right because in tablet mode the 12" ~2 kg laptop is often held with both hands and only edges are thumb-reachable; right side is near Enter/arrows) sits above the keyboard. `osk.modalButton`: always / tablet (default) / never, every screen; a "touchscreen only" option was dropped because niri IPC cannot tell which output a touch device maps to and the user plans an external touch screen. Lock screen (stage 2, built 2026-11-08): session lock hides all layer surfaces, so `LockContent` has its own `OskKeyboard` with `direct: true` — keys become `typed`/`command` signals that edit the password field in-process (no rtfs-vkbd, keys never leave qs); local Shift (one-shot) / Caps state, Shift xor Caps for letters; keys useless for a password (F-keys, Ctrl/Alt/Super, Tab, Del, arrows) are dimmed and inert; no input while PAM is busy. Toggle state `LockScreen.oskShown` is separate from `Osk.shown` (copied from it on lock/preview). Key logic verified by a windowless test (`aA1!Bc '`); the field editing itself only via preview by the user. US layout labels assumed. Launcher (2026-11-10): same pattern as modals — `Launcher.shown` counts in `Osk.modals`, every launcher/mask window has a `DialogOskButton`, and the launcher draws its own `OskKeyboard` (`viewControls: false`) only on the niri-focused screen (where rtfs-vkbd keys land); that screen re-lays its grid in the height above the keyboard.

**Why:** user wants a laptop-style OSK that can switch fcitx5 IMs, like GJS OSK under GNOME.

Cut over 2026-11-08 in the niri project: wvkbd spawn removed, Mod+Shift+O → `qs ipc call osk toggle` (verified by sending Mod+Shift+O through rtfs-vkbd), `wvkbd` dropped from my-niri Depends and moved to its packages.md removal list (still installed for rollback).

**How to apply:** keep the no-`modifiers` rule if the helper changes. See [[open-work]].

rtfs-type (2026-11-09/10) reuses rtfs-vkbd by piping to its stdin. Measured: writing all events at once right after spawning rtfs-vkbd dropped keys near the start; fixed by spawning first and then waiting (≥50 ms, overlapping the 300 ms modifier-release delay) plus a 5 ms gap between events. User verified no drops and that 300 ms is enough to release the hotkey. Keep both if the helper changes.
