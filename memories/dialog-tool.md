Phase 1 2026-11-06, completed to "all zenity/yad/kdialog components + full zenity adapter" the same day (user's goal for the dialog session). Layers, agreed with the user:
- **Adapters** (`scripts/rtfs-zenity`; yad/kdialog adapters not written yet): translate their CLI into a spec and the result back into stdout + exit codes. Only adapters know zenity. Target: every option in the zenity 4.1.90 manual; behavior the manual doesn't describe follows the 4.1.90 source (`gitlab.gnome.org/GNOME/zenity`, tag 4.1.90); undocumented corner cases (e.g. options used with the wrong dialog type) are deliberately not handled. Deliberate differences are listed in its docstring.
- **`scripts/rtfs-ui`**: frontend-agnostic client (spec JSON in, result JSON out; `--stream` for updates/events). Full protocol in its docstring. **`scripts/rtfs-portal`**: file chooser via xdg-desktop-portal (user's choice: no own file browser for now; GNOME portal backend draws it — not Qt's dialog). Since 2026-11-07 it is called only by the shell: container `file` (`shell/DialogFile.qml`, spec title/save/directory/multiple/filename/filters[{name,patterns}]/timeout → values.paths), so rtfs-ui `file` and rtfs-zenity `--file-selection` just send a spec; user wants a possible own chooser later to replace only DialogFile.qml. Verified: xdg-desktop-portal closes the dialog itself when the client disconnects (SIGKILL on Process destroy, qs reload, rtfs-ui interrupted). Linked as `~/bin/rtfs-ui`, `~/bin/rtfs-zenity`. **rtfs-ui subcommand CLI** (2026-11-07, user wanted `xxx warning --text ...` discoverable via `--help` instead of remembering the JSON schema): argparse subcommands info/warning/error/question/entry/password/list/text/scale/number/calendar/color/font/progress/osd in `cli_parser()`; dispatch = first arg is `-h`/`--help` or starts with a letter, otherwise JSON mode (unchanged). User's choices: native CLI inside rtfs-ui (not extending rtfs-zenity), plain-text stdout + exit codes 0 ok/any custom button, 1 cancel/dismiss, 5 timeout, 2 error (`--json` prints the raw result). Main field id is always `v`. `file` subcommand prints one path per line. Not exposed: forms, icons, image, drop, button fields (use JSON mode).
- **`shell/Dialogs.qml`**: one IPC target `ui` (ping/open/update/close/take + `ready` signal). "rtfs-ui is a UI component set", not only modal dialogs (user's view): a spec picks a **container** (`window` = QuickShell `FloatingWindow`, the default like zenity, which is never modal unless `--modal`; `modal` = dimmed overlay, queued one at a time) and lists **fields** (`Field<Type>.qml`, common base `DialogField.qml`); a third container `osd` (2026-11-07) goes to the `Osd` singleton (shared with the shell's own OSDs; one at a time, new replaces old → old request ends with reason `replaced`; the client waits until it disappears, user's choice, revisit if impractical). Fields: entry, number, text, label, check, list, scale, calendar, color, font, progress, image, icons (incl. app picker), drop, button. New kinds = new field types/spec keys, not new IPC targets.
- **Shared QML parts** for every dialog in the shell: `DialogFrame` (modal frame), `DialogBody`, `DialogButton`, `DialogInput`, `DialogCheckBox`, `DialogScrollBar`, `MonthView` (also used by the clock panel's `CalendarView`). In-shell features use these directly, never call rtfs-ui/IPC from inside qs.
- **Colors**: components only use role names from `Theme.dialogDark` / `Theme.dialogLight` (passed via `theme`). Window container = light (TWICE rule "apps light, shell dark"; matches Qt's light title bar, which the user chose to keep instead of drawing our own), modal/ConfirmDialog/PolkitDialog = dark.
- **niri**: window rule `match app-id="^org\.quickshell$"` → `open-floating true` (niri project config; user's choice over a fixed-height trick). Without it resizable windows get tiled.

Protocol details that were verified, not guessed:
- Results/events are **not** broadcast: `ready` signal carries only `<id>` (or `* <generation>` on reload); the client fetches its messages with `take(id, token)` (function return goes only to the caller). Verified with a separate `qs ipc listen` that a password never appears on the signal.
- **Take tokens** (added 2026-11-07; before that any same-uid listener could race `take` with the broadcast id): the first `ping(id)` creates the mailbox and returns a token (later pings return ""); each `take` returns `{token: next, messages}` and rotates it; a wrong token gets `{denied: true}` and rtfs-ui errors out loudly. Tokens are issued by qs, never by the client, because `qs ipc call` argv is readable via `/proc/*/cmdline`; argv only ever shows spent tokens. Randomness is `Math.random` (no CSPRNG in QML; outputs are not observable). Verified: attacker listen+ping+take gets nothing, replaying a spent token is denied, `qs log` does not contain args/return values (QuickShell 0.3.2 server logs only connections). Mailboxes idle > 2 min are dropped only when the request is no longer shown/queued.
- `qs ipc listen` must be connected before results fire → client pings until its ping arrives, then opens. While qs starts/reloads, `ping`/`listen` fail (listen exits) → retry 3 s, restarting listen.
- On reload the dialog is lost: host sends `* <generation>` 500 ms after load; client aborts only if it differs from its ping's generation. See [[qml-gotchas]] for why 500 ms.
- Killing rtfs-zenity forwards SIGTERM/SIGHUP to rtfs-ui, which calls `close`.

Other notes:
- `ConfirmDialog.qml` and the other session's `PolkitDialog.qml` use `DialogFrame`/`DialogButton` (dark). `SystemPopup` (system menu) is a `PanelPopup` dropdown, intentionally not a dialog.
- **Migrated in the main shell session 2026-11-06**: the niri project's former `fuzzel --dmenu` call sites (`niri-tools menu`, `power-profile`, `wallpaper`, `mirror-toggle`) call `rtfs-zenity --list` (hidden index column for `--index` users). Since the window container became the default, they pass `--modal` to keep the overlay look (niri commit 2026-11-06). Killing the *calling* script does not reach `rtfs-zenity` inside `$(...)`.
- Not done: yad/kdialog adapters, tray icon (yad `--notification`/`--appindicator`; user: later), yad notebook/paned (XEmbed), print, loading URLs (no web engine). pinentry (see [[open-work]]) can build on entry fields + `take`.
- Adapter tests live only in the session scratchpad (intercept `run_dialog`, check spec and output/exit codes); rewrite them if the adapter changes a lot.

**Why:** the user wants style/behavior changes to reach every dialog at once and to wrap other dialog CLIs later without touching qs.
**How to apply:** extend the spec + a Field file for new parts, then map in adapters; keep zenity specifics out of rtfs-ui and Dialogs.qml; check zenity's source before guessing its behavior. Related: [[dev-workflow]], [[qml-gotchas]].
