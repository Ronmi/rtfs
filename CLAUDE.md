# rtfs — QuickShell desktop shell for niri

Personal desktop shell built with QuickShell (QML) on top of niri, replacing the community tools in the niri project one component at a time so the desktop feels as consistent as GNOME did.
The user has no prior Qt/QML/QuickShell experience; this is an exploratory project.
Goals, design principles and the component roadmap (for the user, in Chinese) are in `README.tw.md` — read it before starting work. Docs layout (2026-11-20): `README.md` = English entry point for AI agents + the important disclaimers; `README.en.md` = public English README (no author dev notes); `README.tw.md` = Chinese README for the public and the author's own notes (private registry, dev machine); `INSTALL.en.md`/`INSTALL.tw.md` = install guides (AI-assisted prompt + manual steps + hardware support table). Keep disclaimers, requirements and install steps consistent across them.

Use it instead of literal fonts/sizes repeated across components. UI text sizes are always written as `Theme.fontPx(<px at size 14>)` so the `appearance.fonts.uiSize` setting scales them; never a bare `font.pixelSize: 15`.
  - `shell/Dialogs.qml` — `Dialogs` singleton: IPC target `ui`, generic UI described by a JSON spec (used by `scripts/rtfs-ui`): container `DialogWindow` (normal floating window, light), `DialogModal` (dimmed overlay, dark) or `DialogFile` (file chooser; currently runs `scripts/rtfs-portal`, so a future own chooser only replaces this file), content `DialogBody` with fields `Field<Type>.qml` (base `DialogField.qml`). Their colors come from `Theme.dialogDark`/`dialogLight` (role names), never `Colors` directly.

  - `shell/Config.qml` — `Config` singleton: user settings from `~/.config/rtfs/config.yaml` (per machine, outside the project; converted with python3-yaml, reloaded on save). Bad values fall back to defaults with a notification (`Config.notify`). `Config.save(values)` writes only non-default keys (comments are not kept; user accepted).

The part after `var schema =` must stay strict JSON. To add a setting: add it here (a new top-level group also needs its `readonly property var <group>: data.<group>` in `Config.qml`, else `Config.<group>` is undefined and only a runtime warning shows it), use `Config.<group>.<key>`, run `scripts/gen-config-example` (regenerates `config.example.yaml`; never edit that file by hand). The settings window picks it up automatically. Top-level groups are the settings pages, organized by function like GNOME Settings (2026-11-17: appearance = wallpaper + fonts, bar, notifications = timeout + osd, lock, launcher, osk, user); an option of a bar block itself (refresh interval, battery thresholds shown by the menu block) goes under `bar`; nested groups render as sections inside a page. The YAML structure follows the pages, so moving a key is a config-file migration.

Two or more external screens → the menu expands a target list.

Needed because clicking the bar moves focus to the bar's screen. Actions are sent 200 ms after menu/overlay hide.

Entering tablet mode turns it on, leaving turns it off and rotates back to normal; the system-menu tile toggles it in either mode, manual off keeps the current orientation (corner case "manual on in laptop mode, then off while sideways" deliberately left unhandled). Runs `stdbuf -oL monitor-sensor --accel` (iio-sensor-proxy; QuickShell has no generic D-Bus; stdbuf because it block-buffers into a pipe) only while on, plus a one-shot probe at startup (`available`); maps left-up/bottom-up/right-up → niri `Output` `Transform` `"90"`/`"180"`/`"270"` (and `"Normal"`; `_90` is rejected) (verified on the FW12: display accelerometer, touch and pen follow the transform). Rotation briefly nulls `modelData` in per-screen `Variants` delegates; guard with `?.`.

Security-critical: see memory lock-screen.

## Publishing (public snapshot repo)

This repository stays private (full history). The public repository is a separate git repo holding one squashed commit per published version, made in two steps the user insisted on (2026-11-20): `scripts/publish-snapshot prepare [dir] [--ref vX.Y.Z]` exports the tag's files (minus `EXCLUDE` in the script: `.claude/`, `.rmi-work/`, `.forgejo/`, `memories/forgejo-ci.md`, `scripts/publish-snapshot`), stages them and writes a review report (`<dir>/.git/rtfs-snapshot/review.md`: diff stat plus regex hits on added lines — emails, IPs, home paths, private domains, token/key shapes); then a human review (the user, possibly with Claude) of the report, the staged diff, and what regexes cannot see (personal life, machine security details, other people's data, screenshots in `memories/`/docs); only then `scripts/publish-snapshot commit [dir]`, which refuses if the staged tree changed since prepare, commits "rtfs <tag>" and tags it. Never skip or automate the review step, never push for the user. Fix problems in this repo and tag again rather than editing the public tree. The public repo lives in `.rmi-work/public-repo` (the default `dir`; user's choice 2026-11-20): ignored by `.rmi-work/.gitignore`, excluded from snapshots, synced by Syncthing with the rest of the project. The script only accepts an in-project `dir` under an excluded prefix that git ignores. Never run `git clean -X`/`-x` here: it deletes the public repo too.

## Shell code conventions (preliminary, 2026-11-06)

Data sources — use the first that works, and say why when skipping one:
1. QuickShell built-in services (`Quickshell.Services.*` such as UPower, Pipewire, SystemTray, Notifications, Mpris; `Quickshell.Bluetooth`/`Networking`). Event-driven, no extra processes.
2. Socket IPC wrapped in a singleton named after the source (e.g. `Niri.qml`).
3. Reading files directly with `FileView` (sysfs/procfs) plus a `Timer`.
4. `Process` running an existing command; parse in QML.
5. Helper scripts, only when the command logic is complex. Shell-only scripts go in this project's `scripts/`; scripts also useful from a terminal or `nt` belong in the niri project's `scripts/` (its `@summary` header convention) and the shell calls them there. Scripts print JSON for the shell.

Bar colors (user's plan, 2026-11-17): member colors in TWICE age order from the right edge leftwards — system menu nayeon, wireless jeongyeon, OSK momo, tray sana, clock jihyo, network mina, temperature dahyun, workspaces tzuyu (active chaeyoung, urgent jihyo because chaeyoung is taken). Ink by contrast: dark on all fills except tzuyu (light). Keep this order when adding or moving blocks; ask the user before changing it. All eight blocks are always shown (no per-block toggles since 2026-11-17, an empty tray still shows a square sana block), so the color sequence never has a gap.

Files in `shell/`: bar modules `*Block.qml`, popups/panels `*Popup.qml`, data-source singletons named after the source, shared widgets by role (`Tooltip.qml`), assets in `shell/assets/`.
Replacing a waybar module does not delete its niri-side script while `nt` still uses it (e.g. `scripts/battery` → `nt bat`).

## QuickShell

- Installed from the user's own `quickshell` deb (git.ronmi.tw Debian registry, `trixie/main`), pinned to the latest release tag (0.3.2 as of 2026-11-07), not master. It is built by the separate repo `~/raoh/my-quickshell` (Forgejo CI), which also owns the Qt-private-ABI rebuild rule (it links Qt private APIs; the package depends on `qt6-*-private-abi`) and the gcc-not-clang build note. Debian backports has an older 0.3.0 package — do not mix it in. Replaced the former `/usr/local` source build (`build/` here, `~/src/quickshell`) on 2026-11-07.
- Installed files: `/usr/bin/{quickshell,qs}`, QML type info for tooling in Qt's default import path `/usr/lib/x86_64-linux-gnu/qt6/qml/Quickshell/` (modules themselves are statically linked), desktop file and icon.
- Editor tooling (qmlls, user's Emacs `qml-ts-mode` + lsp-mode): `shell/.qmlls.ini` (gitignored) must exist; the running QuickShell replaces it with a symlink to its generated config, whose import paths already include Qt's default path (no `QML_IMPORT_PATH` needed).
- `libcpptrace1` (a `quickshell` dependency) comes from trixie-backports; enable backports on a new machine first.
- Use the documentation for the installed version (quickshell.org has versioned docs); APIs differ between versions. Verify an API exists in the pinned version before using it, rather than relying on memory or examples written for master.
- When a QML/QuickShell concept is used for the first time (bindings, Singletons, PanelWindow, Process, etc.), briefly explain it to the user. Code comments explain *why*, not QML basics.
